数据并行：DDP、ZeRO 与 FSDP

每张卡放一份模型、各吃一份数据、梯度求平均，是最简单的并行。这一页先说明它为什么等价于大 batch、DDP 怎样把通信藏进反向，再看 ZeRO 和 FSDP 如何把每参数 16 字节的模型状态切到 $N_d$ 张卡上，以及要多付多少通信。

数据并行

数据并行（data parallelism, DP）：$N_d$ 张卡各存一份完整模型，各处理不同的样本；反向后把各卡的梯度求平均（all-reduce），每张卡做同样的更新，所以参数始终一致。

记号（本页沿用 ZeRO 论文：参数个数记 $\Psi$）
符号含义形状 / 单位
$N_d$数据并行组的卡数（即这一组的 rank 数 $p$）标量
$B$每卡一个 micro-batch 的样本数标量
$x_{ij}$第 $i$ 张卡上的第 $j$ 个样本—
$\ell(x;\theta)$单个样本的损失标量
$g_i$第 $i$ 张卡的本地梯度同 $\theta$，$\Psi$ 个元素
$\bar g$all-reduce 后的平均梯度同 $\theta$
$\Psi$模型参数个数标量

  1. 全局 batch 有 $N_dB$ 个样本，损失是它们的平均，可以按卡分组：

    $$L(\theta)=\frac{1}{N_dB}\sum_{i=1}^{N_d}\sum_{j=1}^{B}\ell(x_{ij};\theta)=\frac{1}{N_d}\sum_{i=1}^{N_d}\underbrace{\frac1B\sum_{j=1}^{B}\ell(x_{ij};\theta)}_{L_i(\theta)}$$

  2. 求导是线性的，全局梯度就是各卡本地梯度的平均：

    $$\nabla L(\theta)=\frac{1}{N_d}\sum_{i=1}^{N_d}g_i,\qquad g_i=\nabla L_i(\theta)$$

  3. all-reduce 求和再除以 $N_d$，每张卡拿到同一个 $\bar g$。初始参数相同（DDP 构造时从 rank 0 广播），更新规则 $U$ 相同，参数就一直相同：

    $$\theta^{t+1}=\theta^{t}-\eta\,U(\bar g^{\,t})$$

  4. 样本独立同分布、单样本梯度方差为 $\sigma^2$ 时，平均梯度的方差按全局 batch 下降：

    $$\operatorname{Var}[\bar g]=\frac{\sigma^2}{N_dB}$$

所以 DP 只是把全局 batch 放大到 $N_dB$。卡数翻倍而每卡 batch 不变时全局 batch 也翻倍，学习率通常要跟着调（线性缩放规则，Goyal et al. 2017）；超过「临界 batch」后，步数不再按比例减少（McCandlish et al. 2018），这限制了单靠 DP 能用多少卡。每卡放不下想要的 batch 时用梯度累积，见 显存与算力账：梯度累积。

易错

按 token 平均的损失。各卡 token 数不同（变长序列、掩码）时，先卡内按 token 平均、再卡间平均，等于给 token 少的卡加了权。要和单卡大 batch 一致，应该卡内求和、除以全局 token 总数（先 all-reduce 一次 token 计数）。

BatchNorm。它的均值方差只在本卡样本上算，DP 下不等价于大 batch；需要全局统计时用 SyncBatchNorm。LayerNorm / RMSNorm 按样本归一化，不受影响。

DDP：梯度分桶，边反向边通信

DDP（PyTorch DistributedDataParallel）给每个参数挂一个 autograd hook；一个桶里的梯度全部就绪，就在通信流上异步发起这个桶的 all-reduce，和剩下各层的反向计算同时进行。

  • 参数按 model.parameters() 的逆序装桶（近似反向计算的顺序）。桶上限 bucket_cap_mb 默认 25 MiB，第一个桶 1 MiB，好让通信尽早开始；第一次迭代后按实际就绪顺序重建桶。
  • 梯度写在桶的连续缓冲里，一个桶一次 all-reduce，而不是每个参数一次；gradient_as_bucket_view=True 让 .grad 直接指向桶缓冲，省一份拷贝。
  • 某些参数在一步里不参与计算时要开 find_unused_parameters=True，否则那个桶永远等不齐。

  1. 一个 $S$ 字节的桶，用 ring all-reduce 在 $p$ 张卡间同步，按 α-β 模型（见 集合通信：代价模型）用时：

    $$T(S)=\alpha+\frac{2(p-1)}{p}\cdot\frac{S}{\beta}$$

  2. 全部梯度 $S_\text{tot}$ 分成 $n$ 个桶，通信总时长里固定开销随桶数线性增长：

    $$T_\text{comm}=n\alpha+\frac{2(p-1)}{p}\cdot\frac{S_\text{tot}}{\beta}$$

  3. 只有反向结束后通信还没做完的那段 $T_\text{exposed}$ 才拉长一步：

    $$T_\text{step}\approx T_\text{fwd}+T_\text{bwd}+T_\text{exposed}+T_\text{opt}$$

  4. 桶太小，$n\alpha$ 变大；桶太大，最后一桶要等反向几乎做完才发出、而且大，$T_\text{exposed}$ 变大。

梯度累积

前几个 micro-batch 放在 with model.no_sync(): 里，梯度只在本地累加、不发 all-reduce；最后一个 micro-batch 正常反向，一次同步累加好的梯度。

ZeRO：把模型状态切成 $N_d$ 份

ZeRO（Zero Redundancy Optimizer，Rajbhandari et al. 2020）：DP 里每张卡都存一整份参数、梯度和优化器状态，这是冗余的。ZeRO 把它们沿参数维切成 $N_d$ 片，每卡长期只存自己那一片，用到别的片时再通信取回。三个阶段依次多切一样东西。

混合精度 Adam 每个参数占 16 字节：BF16 参数 2、BF16 梯度 2、FP32 主权重与一阶、二阶矩共 $K=12$（来由见 显存与算力账：显存账）。激活不在其中，ZeRO 的数据并行部分也不切激活。

记号
符号含义单位
$\Psi$参数个数个
$N_d$数据并行组的卡数张
$K$每参数优化器状态的字节数（混合精度 Adam 为 12）字节
$M_k$ZeRO-$k$ 下每卡模型状态显存字节

  1. DP：每卡全存。

    $$M_\text{DP}=(2+2+K)\Psi=16\Psi$$

  2. ZeRO-1（$P_{os}$，切优化器状态）：每卡只负责更新 $1/N_d$ 的参数，只需要这部分的 FP32 主权重和矩。

    $$M_1=2\Psi+2\Psi+\frac{K\Psi}{N_d}$$

  3. ZeRO-2（$P_{os+g}$，再切梯度）：一片梯度只在负责更新它的那张卡上需要求和结果，reduce-scatter 之后别的卡就可以丢掉。

    $$M_2=2\Psi+\frac{(2+K)\Psi}{N_d}$$

  4. ZeRO-3（$P_{os+g+p}$，再切参数）：参数平时也只存一片，前向、反向用到某一层时再 all-gather。

    $$M_3=\frac{(2+2+K)\Psi}{N_d}$$

  5. 论文的例子：$\Psi=7.5\text{B}$、$N_d=64$ 时四者依次是 120、31.4、16.6、1.9 GB。

通信量

下面以元素个数计，忽略 $(p-1)/p$ 因子，和论文一致。

  1. DP 的梯度 all-reduce 等于一次 reduce-scatter 加一次 all-gather，各传约 $\Psi$（见 集合通信：恒等式）：

    $$C_\text{DP}=\underbrace{\Psi}_\text{RS}+\underbrace{\Psi}_\text{AG}=2\Psi$$

  2. ZeRO-1/2 把这两步拆开用：reduce-scatter 梯度 → 每卡用自己那片梯度更新自己那片参数 → all-gather 新参数。总量不变：

    $$C_{1}=C_{2}=\Psi+\Psi=2\Psi$$

  3. ZeRO-3 不常驻完整参数：前向 all-gather 一次，反向再 all-gather 一次，梯度 reduce-scatter 一次；更新后不必再 all-gather，下一步前向会取。

    $$C_3=\Psi+\Psi+\Psi=3\Psi=1.5\,C_\text{DP}$$

ZeRO-1/2 白省显存，不加通信；ZeRO-3 把显存降到 $1/N_d$，代价是多 50% 通信，而且前向的 all-gather 挡在计算前面，必须靠预取藏起来（下一节）。

相关

Adam 是逐元素更新，参数怎么切都能就地算；Muon 这类按整块矩阵运算的优化器需要完整的梯度矩阵，和 ZeRO 的扁平切分冲突，做法见 优化器：分布式 Muon。

Megatron-Core 的 distributed optimizer 属于 ZeRO-1 一类：切 FP32 主权重和优化器状态，梯度 reduce-scatter、新参数 all-gather，常和 TP / PP 一起用。

FSDP：逐单元取回，用完即弃

FSDP（Fully Sharded Data Parallel，Zhao et al. 2023）是 PyTorch 里的 ZeRO-3：把模型分成若干单元（通常一个 Transformer block 一个），每个单元的参数平时只存 $1/N_d$；轮到它计算时 all-gather 成完整参数，算完马上释放。

一步的执行顺序

  1. 前向，单元 $k=1\dots L$：all-gather 参数 → 前向 → 释放完整参数（reshard），只留本卡那片。
  2. 反向，单元 $k=L\dots1$：all-gather 参数 → 反向得到完整梯度 → reduce-scatter，每卡留自己那片梯度 → 释放完整参数和完整梯度。
  3. 优化器：每卡只更新本卡那片参数，不需要通信。

预取：单元 $k$ 计算时就发出下一个单元（反向时是 $k-1$）的 all-gather，通信藏在计算后面。同一时刻最多保留两个完整单元（当前 + 预取）；FSDP1 的 limit_all_gathers 就是这个限流，防止 CPU 发指令太快、一次分配太多完整单元。

记号
符号含义单位
$L$单元个数个
$\Psi_u$一个单元的参数个数（$\Psi\approx L\Psi_u$）个
$A_k$单元 $k$ 为反向保存的激活字节

  1. 常驻的是切开的模型状态：

    $$M_\text{shard}=\frac{16\Psi}{N_d}$$

  2. 反向开始时激活最多；此时完整的有当前和预取两个单元的 BF16 参数，加当前单元的完整梯度：

    $$M_\text{peak}\approx\frac{16\Psi}{N_d}+2\cdot2\Psi_u+2\Psi_u+\sum_{k=1}^{L}A_k$$

  3. 单元越大，第二、三项越大；单元越小，集合通信次数 $3L$ 越多，固定开销 $\alpha$ 越难摊薄。整个模型当一个单元时第二项变成 $2\Psi$ 字节，等于退回 ZeRO-2。

reshard_after_forward

  • True（非根单元的默认值）：前向后释放，反向再 all-gather 一次，通信 $3\Psi$。
  • False：完整参数一直留到该单元反向结束，省掉反向那次 all-gather，通信 $2\Psi$，但前向结束时所有单元都是完整的，效果接近 ZeRO-2（FSDP1 里叫 SHARD_GRAD_OP）。根单元默认 False，因为反向一开始就要用它。
  • 整数 $k$（FSDP2）：前向后只切到 $k$ 张卡（例如一个节点的 8 卡），反向的 all-gather 只在节点内做，显存介于两者之间。

FSDP1 与 FSDP2

FSDP1（FullyShardedDataParallel）把一个单元的所有参数拼成一维的 FlatParameter 再均分，一个单元一次通信；但同一单元的参数需要同一 dtype，冻结其中一部分也要额外处理。FSDP2（fully_shard，PyTorch 2.6 起在 torch.distributed.fsdp 下）把每个参数单独沿第 0 维切成 DTensor（Shard(0)），优化器直接作用在 DTensor 上，state dict 也是切开的，和 TP 组成二维并行更直接。

from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.layers:
    fully_shard(block, mp_policy=mp)   # 每个 block 一个单元
fully_shard(model, mp_policy=mp)       # 根单元：嵌入、输出层等其余参数
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)   # 在切开的 DTensor 上建优化器
FSDP2 的 16 字节

常见配法是本卡分片存 FP32 参数，param_dtype=bf16 让 all-gather 和计算用 BF16，reduce_dtype=fp32 让梯度按 FP32 归约：每参数 4（FP32 参数）+ 4（FP32 梯度）+ 8（$m,v$）= 16 字节再除以 $N_d$。总数和 ZeRO 的 $2+2+12$ 一样，只是没有常驻的 BF16 副本；代价是 FP32 的 reduce-scatter 字节数翻倍。

易错

梯度累积时如果跳过 reduce-scatter（FSDP2 的 set_requires_gradient_sync(False)），每个单元的完整梯度都要留到最后一个 micro-batch，显存涨到整模型梯度的规模；每个 micro-batch 都 reduce-scatter 则通信乘以累积步数。显存紧时选后者。

HSDP 与 ZeRO++：让通信留在节点内

HSDP（hybrid sharded data parallel）：在每个节点的 $G$ 张卡之间做 FSDP，在 $n$ 个节点之间做复制。同一片参数在每个节点各有一份，节点间只对梯度片做 all-reduce。

记号
符号含义单位
$n$节点数个
$G$每节点卡数，也是 HSDP 的切分组大小张
$M$一份 BF16 完整参数（或梯度）的大小，$M=2\Psi$字节
$V$每个节点每步经网卡发出的数据量字节

  1. 每卡模型状态只切到节点内：

    $$M_\text{HSDP}=\frac{16\Psi}{G}\qquad\text{对比}\qquad M_\text{FSDP}=\frac{16\Psi}{nG}$$

  2. 跨 $n$ 个节点做一次 all-gather 或 reduce-scatter，每个节点至少要发出（收进）其余节点那部分数据，ring 类算法正好达到：

    $$V_\text{AG}=V_\text{RS}=\frac{n-1}{n}M$$

  3. 全局 FSDP 的两次 all-gather 和一次 reduce-scatter 都跨节点：

    $$V_\text{FSDP}=3\cdot\frac{n-1}{n}M$$

  4. HSDP 的 all-gather / reduce-scatter 都在节点内（NVLink）；跨节点只有梯度片的 all-reduce，节点里 $G$ 张卡各管 $M/G$：

    $$V_\text{HSDP}=G\cdot\frac{2(n-1)}{n}\cdot\frac{M}{G}=2\cdot\frac{n-1}{n}M$$

HSDP 的跨节点流量和 DDP 一样，比全局 FSDP 少三分之一；参与每次跨节点集合通信的只有 $n$ 个 rank，延迟更小；而且 FSDP 的跨节点 all-gather 挡在前向关键路径上，HSDP 的跨节点 all-reduce 只出现在反向里、可以和计算重叠。代价是每卡显存只降到 $1/G$。FSDP2 里传一个二维 DeviceMesh (replicate, shard) 就是 HSDP；FSDP1 对应 ShardingStrategy.HYBRID_SHARD。

ZeRO++

ZeRO++（Wang et al., ICLR 2024）在 ZeRO-3 上改了三处通信：qwZ 把前向 all-gather 的权重按块量化成 INT8；hpZ 在每个节点内多存一份按节点切的参数，反向 all-gather 只在节点内做（以显存换通信，和 FSDP2 整数版 reshard_after_forward 同一思路）；qgZ 把梯度量化成 INT4，用分层 all-to-all 代替 reduce-scatter。三者合起来跨节点通信量降为 ZeRO-3 的 1/4，论文在 384 卡上报告最高 2.16 倍吞吐。

Offload：把状态放到 CPU 和 NVMe

Offload：卡少、显存是唯一瓶颈时，把优化器状态（甚至参数）放到 CPU 内存或 NVMe，用 PCIe 带宽和 CPU 算力换显存。

ZeRO-Offload（Ren et al. 2021）的划分：前向、反向在 GPU 上，GPU 只存 16 位参数；FP32 主权重、$m$、$v$ 和梯度放在 CPU，Adam 在 CPU 上跑（DeepSpeed 的 CPU-Adam 用 SIMD 和多线程加速）。论文在单张 V100 上训练了超过 130 亿参数的模型。

  1. 两边各存什么：

    $$M_\text{GPU}=2\Psi+\text{激活},\qquad M_\text{CPU}=\underbrace{12\Psi}_{\text{FP32 主权重}+m+v}+\underbrace{2\Psi}_{\text{梯度}}$$

  2. 每步 PCIe 搬两次：梯度下行、新参数上行。

    $$V_\text{PCIe}=2\Psi+2\Psi=4\Psi\ \text{字节}$$

  3. 梯度下行可以和反向重叠，但 CPU 更新要等梯度到齐，GPU 又要等新参数：

    $$T_\text{step}\approx T_\text{GPU}+T_\text{剩余梯度下行}+T_\text{CPU-Adam}+T_\text{参数上行}$$

  4. 延迟一步更新（DPU）：第 $t$ 步的 CPU 更新和第 $t+1$ 步的 GPU 计算并行，第 $t+1$ 步用的参数还没包含第 $t$ 步的梯度。稳态下：

    $$T_\text{step}\approx\max\big(T_\text{GPU},\ T_\text{梯度下行}+T_\text{CPU-Adam}+T_\text{参数上行}\big)$$

论文只在训练开头若干步之后才打开 DPU，避开早期梯度变化最快的阶段。ZeRO-Infinity（Rajbhandari et al. 2021）在 ZeRO-3 上把参数、梯度、优化器状态都可以放到 CPU 或 NVMe、按需预取，论文报告在 32 台 DGX-2（512 张 V100）上可容纳 32T 参数的模型。PyTorch FSDP2 用 offload_policy=CPUOffloadPolicy() 把分片参数、梯度和优化器计算放到 CPU。

自测

8 卡 DDP、每卡 batch 32，和单卡 batch 256 的一步更新一样吗？什么情况下不一样？

损失按全局样本平均时，梯度在数学上相同（只差浮点求和顺序）。不一样的情况：BatchNorm 只用本卡统计量；损失先在卡内按 token 平均、各卡 token 数又不同；dropout 等随机数在各卡上不同。

DDP 的桶设成 1 MB 和 2 GB，各会出什么问题？

1 MB：桶数多，每次 all-reduce 的固定开销 $\alpha$ 累加起来很大。2 GB：所有梯度算完才凑满一桶，几乎没有重叠，等于反向结束后一次性通信。

7.5B 模型在 64 卡上用 ZeRO-2，每卡模型状态多少？为什么通信量和 DDP 一样？

$2\Psi+14\Psi/64\approx15+1.6=16.6$ GB。DDP 的 all-reduce 本来就是 reduce-scatter 加 all-gather，ZeRO-2 只是在两步之间插入「各卡只更新自己那片」，总量仍是 $2\Psi$。

ZeRO-3 / FSDP 的 $3\Psi$ 是哪三次？哪一次可以省，代价是什么？

前向 all-gather、反向 all-gather、梯度 reduce-scatter。设 reshard_after_forward=False 可以省掉反向那次 all-gather，代价是前向后完整参数一直留到反向，显存退回接近 ZeRO-2。

FSDP 为什么通常一个 Transformer block 一个单元？把整个模型当一个单元会怎样？

整个模型一个单元时，all-gather 出的完整参数（$2\Psi$ 字节）一直占着，也没有下一个单元可以预取，通信无法和计算重叠。按 block 切，峰值只多两个 block 的参数，且每个单元的 all-gather 可以藏在上一个单元的计算后面。

4 节点 × 8 卡、Ψ = 13B，HSDP 和全局 FSDP 每卡模型状态各多少？每节点跨节点流量呢？

显存：$16\Psi/8=26$ GB 对 $16\Psi/32=6.5$ GB。$M=2\Psi=26$ GB，跨节点：HSDP $2\cdot\tfrac34M=39$ GB，FSDP $3\cdot\tfrac34M=58.5$ GB。

ZeRO-Offload 每步 PCIe 要搬多少数据？DPU 换来了什么、牺牲了什么？

梯度下行 $2\Psi$ 加参数上行 $2\Psi$，共 $4\Psi$ 字节。DPU 让 CPU 更新和下一步的 GPU 计算并行，消掉 GPU 空等；代价是 GPU 用的参数落后一步，所以只在训练开头若干步之后才打开。
