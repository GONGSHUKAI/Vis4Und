Coding Agent 的训练

Coding agent = 语言模型 + 一套工具（bash、看文件、改文件）+ 一个循环。训练它要三样东西：能跑测试的任务环境、从强模型轨迹做的 SFT 冷启动、以测试是否通过为奖励的多轮 RL。策略梯度和 GRPO 的记号沿用补充篇。

读完能回答

  • 一条多轮轨迹里，哪些 token 计入 loss？为什么？
  • SWE-bench 怎么判定「解决了」？FAIL_TO_PASS 和 PASS_TO_PASS 各管什么？
  • 一个可训练的任务实例由哪几部分构成，合成数据怎么批量造？
  • 同步 rollout 为什么会让 GPU 空转？异步的代价是什么？
  • SWE-RL、DeepSWE、Kimi-Dev、Qwen3-Coder 这些开源配方各用了什么环境、算法和 scaffold？

什么是 coding agent

Coding agent：模型在一个循环里交替「输出一段思考和一个工具调用」和「读工具返回的结果」，直到它调用 submit；最终产物是对仓库的一个补丁（diff）。

  • Scaffold（也叫 harness）：负责把工具描述写进系统提示、解析模型输出里的工具调用、在沙箱里执行、把结果拼回上下文。同一个模型换 scaffold，SWE-bench 分数能差很多，所以报分必须注明 scaffold。
  • 工具：最小集合是 bash；常见的还有文件查看 / 按字符串替换编辑（str_replace）、搜索、提交。mini-SWE-agent 只给 bash。
  • ReAct 循环：思考（reason）→ 动作（act）→ 观察（observation），重复。每一轮的观察都追加到上下文，轨迹越长上下文越长。
  • 上下文管理：测试日志、文件内容可能有上千 token。常见做法是截断长观察（只留头尾）、只保留最近几轮的完整观察、把更早的历史压缩成摘要。

怎么评测：SWE-bench 一族

SWE-bench 任务实例：一个真实 GitHub issue，加上提出它时的仓库快照（base commit），以及修复它的 PR。PR 里的代码改动是参考答案（gold patch），PR 里的测试改动用来评分，agent 看不到这些测试。

评分用的两组测试
名称含义作用
FAIL_TO_PASS在 base commit 上失败、打上 gold patch 后通过的测试检查 issue 真的被修了
PASS_TO_PASS打补丁前后都通过的测试检查没有改坏别的功能
$$\text{resolved}=\Big[\bigwedge_{t\in\text{F2P}}\text{pass}(t)\Big]\wedge\Big[\bigwedge_{t\in\text{P2P}}\text{pass}(t)\Big],\qquad \text{分数}=\frac{\#\text{resolved}}{\#\text{实例}}$$

评测流程：在该实例的 Docker 镜像里检出 base commit → 应用 agent 的补丁 → 把测试文件恢复成 PR 里的版本 → 只跑 F2P 和 P2P 里的测试，按日志判定通过与否。

任务环境与数据

可训练的任务实例 = 仓库快照 + 任务描述（issue）+ 装好依赖的 Docker 镜像 + 能判定成功的测试（F2P / P2P）。参考补丁只用来验证实例有效，不给 agent 看。

真实 issue 能直接用的不多：大量 PR 没有配套测试，依赖装不起来，测试不确定性高。所以出现了两条路：

  • 挖真实数据：自动化地爬 PR、搭环境、跑测试，留下「打 gold patch 前后测试结果确实翻转」的实例。SWE-Gym、SWE-rebench 属于这一类。
  • 合成：在本来测试全过的仓库里人为引入 bug，让一些测试失败，这些测试就是 F2P；再让 LM 根据失败的测试写一段 issue。SWE-smith、R2E-Gym 属于这一类，规模更容易扩大。

训练配方

公开配方大体是三段，每一段都可以省略或合并：

  1. 继续预训练 / mid-training：大量代码、仓库级上下文、合成的 agent 轨迹，让基座熟悉「读仓库、跑命令、读日志」的格式。闭源细节最多的一段。

  2. SFT（冷启动）：用更强的模型在环境里跑 agent，只保留最终补丁通过测试的轨迹（rejection sampling），按多轮对话格式微调，loss 只算模型 token。

  3. 多轮 RL：策略自己在沙箱里跑，奖励是隐藏测试是否通过，用 GRPO / PPO 类算法更新。环境越多、越难、越「刚好在能力边界」，RL 收益越大。

两种采样都依赖任务对当前模型的难度。设某任务的单次成功率为 $p$：

$$P(\text{k 次里至少成功一次})=1-(1-p)^k,\qquad P(\text{GRPO 组有梯度})=1-p^G-(1-p)^G$$

多轮目标与 loss mask

记号
符号含义形状
$x$系统提示 + issuetoken 序列
$a_k$第 $k$ 轮模型输出（思考 + 工具调用）token 序列
$o_k$第 $k$ 轮工具 / 环境返回的观察token 序列
$h_k$第 $k$ 轮开始时的历史 $(x,a_1,o_1,\dots,a_{k-1},o_{k-1})$token 序列
$\tau$整条轨迹，共 $K$ 轮，拼成 token 序列 $z_1,\dots,z_L$长度 $L$
$P_\text{env}(o_k\mid h_k,a_k)$沙箱执行工具调用的结果分布，与 $\theta$ 无关—
$m_t$loss mask：$z_t$ 是模型生成的为 1，否则为 0$\{0,1\}$
$R(\tau)$提交后隐藏测试给的奖励标量

  1. 轨迹概率是模型和环境交替的乘积：

    $$p_\theta(\tau)=\prod_{k=1}^{K}\pi_\theta(a_k\mid h_k)\,P_\text{env}(o_k\mid h_k,a_k)$$

  2. 取对数再对 $\theta$ 求导，环境项是常数，消失：

    $$\nabla_\theta\log p_\theta(\tau)=\sum_{k=1}^{K}\nabla_\theta\log\pi_\theta(a_k\mid h_k)$$

  3. 每个 $a_k$ 再拆成 token，正好是序列里 $m_t=1$ 的位置；观察 token 只作为条件出现在 $z_{<t}$ 里：

    $$\nabla_\theta\log p_\theta(\tau)=\sum_{t=1}^{L}m_t\,\nabla_\theta\log\pi_\theta(z_t\mid z_{<t})$$

  4. 代入策略梯度（推导见补充篇）：

    $$\nabla_\theta J=\mathbb E_{\tau}\Big[R(\tau)\sum_{t}m_t\,\nabla_\theta\log\pi_\theta(z_t\mid z_{<t})\Big]$$

  5. 同一任务采 $G$ 条轨迹，用组内基线、token-mean 聚合（只数 mask 内的 token），就是常见的多轮 GRPO / DAPO 目标：

    $$\mathcal J=\mathbb E\Bigg[\frac{1}{\sum_i\sum_t m_{i,t}}\sum_{i=1}^{G}\sum_{t}m_{i,t}\min\big(\rho_{i,t}\hat A_i,\ \operatorname{clip}(\rho_{i,t},1-\epsilon_\text{low},1+\epsilon_\text{high})\hat A_i\big)\Bigg],\quad \hat A_i=\frac{R_i-\bar R}{\operatorname{std}(R)}$$
易错

重新分词：如果把历史先解码成文本、下一轮再重新分词，得到的 token 可能和模型当时采样的不一样，$\log\pi_\text{old}$ 就对不上。做法是全程保存 token id（token-in, token-out），只把观察部分新分词后拼上去。

被截断的轨迹：撞上最大轮数、上下文或时间上限的轨迹没有真正的结局，直接给 0 分会惩罚「还没做完」。常见做法是把这类轨迹整条 mask 掉，不参与 loss。

信用分配粗：$\hat A_i$ 对整条轨迹所有模型 token 相同，几十轮里哪一步关键分不出来。这是多轮 agent RL 目前的主要难点之一。

Rollout 基础设施

一条 SWE 轨迹要几十轮、每轮都要在容器里执行命令，长度从几千到十几万 token 不等，耗时长尾很重。训练系统要同时管：

  • 沙箱：每条轨迹一个容器（每个任务实例一个镜像），成百上千个并发；命令要有超时，容器要能快速创建和回收。
  • 推理引擎：vLLM / SGLang 做多轮生成，保留 KV cache 前缀；权重每个训练步后同步过来。
  • 调度：同步还是异步，允许多大的陈旧度，长轨迹能否中途换新权重（partial rollout）。

奖励设计与 reward hacking

最常见的奖励是二值的 resolved：隐藏的 F2P 与 P2P 全部通过得 1，否则 0（有的配方给格式错误、超时额外负分）。也有别的设计：

  • 测试通过比例（部分分）：信号更密，但修一半也拿分，模型可能学会只修容易的那部分。
  • 补丁相似度（SWE-RL）：不执行代码，奖励是模型补丁和参考补丁的序列相似度，格式错误给 −1。好处是不需要可执行环境，能用海量 PR 数据；坏处是不同但正确的修法拿不到满分。

只要奖励由一个可被策略影响的程序计算，策略就会去找它的漏洞。对 coding agent，漏洞多半来自「判分时跑的是什么测试、在什么状态下跑」。

对应的防护：判分只用 agent 看不到的测试，并在跑之前把测试文件恢复原状；P2P 要覆盖足够多的既有功能；隐藏测试的输入不要只是 issue 里的例子；仓库快照里不留包含答案的后续提交；训练中抽查高奖励轨迹，监控「改了测试文件」「补丁里出现针对测试的分支」这类信号。

自测

一条 30 轮的轨迹里，pytest 的输出 token 要不要算 loss？

不算。轨迹概率里环境项 $P_\text{env}(o_k\mid h_k,a_k)$ 与 $\theta$ 无关，求导后消失，所以只有 $m_t=1$ 的模型 token 有梯度。若把观察也算进去，模型会被训练去「预测」测试日志，目标就错了。

补丁修好了 issue，但另一个原本通过的测试挂了，SWE-bench 算解决吗？

不算。挂掉的测试属于 PASS_TO_PASS，resolved 要求 F2P 全过且 P2P 全过。

用 SWE-smith 的方式注入一个 bug 后，所有测试仍然通过，这个候选怎么处理？

丢弃。没有 FAIL_TO_PASS 测试就无法判定「修好了」，也说明这个改动在现有测试下不可观测。

某任务当前模型的成功率约 0.02，用 G = 8 的 GRPO 训练，这个任务能提供多少学习信号？

一组有梯度的概率是 $1-0.02^8-0.98^8\approx0.15$，大多数组白采。这类任务更适合先靠 SFT（强模型轨迹）或更大的 $G$、课程式筛选来处理。

同步 rollout 时 GPU 空转主要来自哪两部分？

一是等最慢的轨迹（长尾）时，已完成轨迹的推理槽空着；二是训练这段时间推理端停着（同一批 GPU 轮流做推理和训练时）。异步把两者重叠，代价是样本陈旧，需要重要性比值修正。

为什么判分前要把测试文件恢复成参考版本？

否则 agent 改测试、删测试、把断言改成恒真都能让「测试通过」，奖励和「修好了 issue」脱钩。恢复后，判分用的测试完全不受 agent 补丁影响。

两个模型的 SWE-bench Verified 分数能直接比吗？要看哪些条件？

要看 scaffold（OpenHands、SWE-agent、Agentless、自研）、最大轮数和上下文、是 pass@1 还是 best-of-N 加验证器、是否用了测试时扩展。同一模型在不同条件下能差十几个点。
