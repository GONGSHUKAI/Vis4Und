(4) 分布式训练 · (iii)

集合通信

所有并行策略最后都落到少数几个通信原语上：梯度用 all-reduce，FSDP 用 all-gather 和 reduce-scatter，MoE 用 all-to-all。这一页讲每个原语做什么、每张卡要收发多少字节、ring 和 tree 两种算法各花多少时间，以及节点内外的带宽差距怎样决定并行维度的摆放。

读完能回答

  • all-reduce 为什么等于 reduce-scatter 加 all-gather？每张卡最少要收发多少数据？
  • ring all-reduce 的带宽项为什么几乎不随卡数增长？它的短板在哪，tree 怎么补？
  • nccl-tests 输出的 algbw 和 busbw 有什么区别，busbw 该拿去和什么比？
  • 节点内 NVLink 和节点间 InfiniBand 差几倍？为什么张量并行一般不跨节点？
  • DDP、FSDP、TP、PP、EP 各自用哪个原语？

八个原语

集合通信（collective）是一组 rank 同时参与的通信操作：组内每个 rank 调用同一个函数、给出各自的缓冲区，调用结束时各 rank 的输出满足约定的关系。与之相对的是两个 rank 之间的点对点通信 send / recv。一个 rank 通常对应一张 GPU。

原语之间的关系

all-gather 和 reduce-scatter 是两个「基本件」，其余几个大消息原语都能拼出来，每卡收发量也就跟着定了。

  1. reduce-scatter：rank $r$ 输入里有 $p-1$ 块归别人所有，每块的信息都必须离开 rank $r$，所以每卡至少发：

    $$V_\text{RS} = \frac{p-1}{p}\,n$$

  2. all-gather：rank $r$ 缺 $p-1$ 块，每块只能从外面收进来，所以每卡至少收：

    $$V_\text{AG} = \frac{p-1}{p}\,n$$

  3. all-reduce 先按块求和、再把和发给所有人，正好是两者串联：

    $$\text{AllReduce}(x) = \text{AllGather}\big(\text{ReduceScatter}(x)\big),\qquad V_\text{AR} = 2\,\frac{p-1}{p}\,n$$

  4. Patarasuk 与 Yuan（2009）证明任何 all-reduce 都至少有一个 rank 发出、一个 rank 收进 $2\frac{p-1}{p}n$，所以「reduce-scatter + all-gather」在带宽上是最优的。同理，大消息的 broadcast 常做成 scatter + all-gather，reduce 做成 reduce-scatter + gather。

为什么 FSDP 不用 all-reduce

FSDP / ZeRO 每张卡只存 $1/p$ 的参数和优化器状态，所以只需要「自己那一块」的梯度和：一次 reduce-scatter 就够，通信量是 all-reduce 的一半；前向前再 all-gather 取回整块参数。两次加起来和一次 all-reduce 一样多，见 ZeRO 的通信量。

α-β 代价模型

α-β 模型（Hockney 模型）把一次点对点传输的时间写成固定启动延迟加字节数乘以每字节时间：$T = \alpha + n\beta$。

记号
符号含义单位
$\alpha$每条消息的启动延迟：软件开销、同步、网络往返s
$B$一个 rank 单方向的链路带宽byte/s
$\beta = 1/B$每字节传输时间s/byte
$n$消息大小byte
$$T_\text{p2p}(n) = \alpha + n\beta,\qquad n_{1/2} = \frac{\alpha}{\beta} = \alpha B$$

$n < n_{1/2}$ 时延迟占大头，叫延迟受限；$n \gg n_{1/2}$ 时带宽占大头，叫带宽受限。例如 $\alpha = 5\,\mu\text{s}$、$B = 50$ GB/s 时 $n_{1/2} = 250$ KB。训练里的梯度、参数通常是几十 MB 到几 GB，带宽受限；loss、梯度范数这类标量是纯延迟受限。集合通信由多步点对点组成，算法的总时间写成 $a\,\alpha + b\,n\beta$，比的就是两项的系数 $a$ 和 $b$。

Ring all-reduce

$p$ 个 rank 连成环，每个 rank 只和下一个 rank 通信，每步每条链路上同时有数据在走，所有链路都不闲着。

  1. 把每个 rank 的缓冲区切成 $p$ 块，每块 $n/p$。

  2. reduce-scatter 阶段：第 $s$ 步（$s=0,\dots,p-2$），rank $r$ 把块 $(r-s) \bmod p$ 发给 rank $r+1$，接收方加到自己的同号块上。每步耗时：

    $$\alpha + \frac{n}{p}\beta$$

  3. $p-1$ 步后，块 $c$ 从 rank $c$ 出发绕了 $p-1$ 跳，累加了所有 rank 的贡献，停在 rank $c-1$：每个 rank 恰好持有一块完整的和。

  4. all-gather 阶段：再走 $p-1$ 步，第 $s$ 步 rank $r$ 把块 $(r+1-s) \bmod p$（已完整）发给下一个，接收方直接覆盖。

  5. 共 $2(p-1)$ 步：

    $$T_\text{ring} = 2(p-1)\,\alpha + 2\,\frac{p-1}{p}\,n\beta$$

  6. 带宽项达到上一节的下界，$p\to\infty$ 时趋于 $2n\beta$，与卡数无关；延迟项随 $p$ 线性增长，卡多、消息小时成为瓶颈。

Tree 与 double binary tree

ring 的步数是 $2(p-1)$。树形算法先沿树把数据归约到根，再从根广播回去，步数只和树高 $\lceil\log_2 p\rceil$ 有关；大消息切成小块流水着走，带宽也能用满。

  1. 二叉树高度 $\lceil\log_2 p\rceil$，归约上行、广播下行各走一遍，延迟项：

    $$2\lceil\log_2 p\rceil\,\alpha$$

  2. 单棵二叉树里约一半 rank 是叶子：广播时叶子只收不发，内部节点要给两个孩子各发一份，链路用得不均匀。

  3. double binary tree（Sanders 等，2009；NCCL 2.4 起用于 all-reduce）建两棵树，各管一半数据。第二棵树把第一棵的叶子换成内部节点，于是每个 rank 在一棵树里是内部节点、在另一棵里是叶子。

  4. 数一下每个 rank 发出的量：做内部节点的那棵树里，上行 $\tfrac{n}{2}$、下行给两个孩子 $2\cdot\tfrac{n}{2}$；做叶子的那棵树里，上行 $\tfrac{n}{2}$。合计 $2n$，与 ring 的 $2\frac{p-1}{p}n$ 几乎相同：

    $$T_\text{tree} \approx 2\lceil\log_2 p\rceil\,\alpha + 2n\beta$$

图里的虚线是 Rabenseifner 的递归减半 + 递归倍增（Thakur 等，2005）：reduce-scatter 每步和距离减半的伙伴交换一半数据，all-gather 反过来，$T = 2\log_2 p\,\alpha + 2\frac{p-1}{p}n\beta$，两项系数同时最小。它在 MPI 里常用，但每步的通信伙伴相距 $p/2, p/4, \dots$，在分层网络上远距离的通信对会挤在同一段上行链路上，实际跑不到模型里的数，这也是 NCCL 主要用 ring 和 tree 的原因。NCCL 2.23 加入的 PAT 是同一思路的变体：只用于 all-gather / reduce-scatter，先处理最远的维度、按缓冲区大小限制聚合量，针对大规模下的中小消息（初版每节点只支持 1 张 GPU）。

algbw 与 busbw

nccl-tests（all_reduce_perf 等）每行输出两个带宽。它的文档里 $S$ 是数组总字节数、$n$ 是 rank 数；下面沿用本页记号，$S$ 照旧、rank 数写作 $p$。

  1. 算法带宽，直接拿数据量除以时间：

    $$\text{algbw} = \frac{S}{t}$$

  2. all-reduce 每个元素要 $p-1$ 次加法和 $p$ 次赋值，至少 $2(p-1)$ 次传输，由 $p$ 条带宽为 $B$ 的链路分担，所以最快：

    $$t = \frac{2(p-1)}{p}\cdot\frac{S}{B}$$

  3. 反解出硬件带宽，就是总线带宽：

    $$\text{busbw} = \text{algbw}\cdot\frac{2(p-1)}{p}$$

  4. 其它原语的修正因子：reduce-scatter、all-gather、all-to-all 是 $\frac{p-1}{p}$；broadcast、reduce 是 $1$（根的那条链路是瓶颈）。

易错

拿 algbw 和链路带宽比会得出误导结论：8 卡 all-reduce 的 algbw 理论上只有链路带宽的 $8/14$，看起来「只用了 57%」，其实已经满了。比较不同卡数的结果、或者和硬件规格比，都用 busbw。

拓扑：节点内与节点间

一台 8 卡服务器（一个节点）里，GPU 之间走 NVLink，经 NVSwitch 全互联；节点之间每张 GPU 通常配一张 InfiniBand 或 RoCE 网卡。两层带宽差将近一个数量级，这是安排并行维度的首要约束。

单位

NVLink 的官方数字是双向合计、单位 GB/s（字节）；网卡是单方向、单位 Gb/s（比特）。换到同一口径：H100 的 NVLink 单向 450 GB/s，NDR 网卡单向 50 GB/s，相差 9 倍。GB200 NVL72 把 NVLink 域扩到 72 卡，官方合计 130 TB/s（= 72 × 1.8 TB/s）。

层次化 all-reduce

$m$ 个节点、每节点 $g$ 张卡（$p = mg$）。先在节点内把数据切成 $g$ 块，再只让「每卡负责的那 $1/g$」过网卡：

  1. 节点内 reduce-scatter（NVLink，带宽 $B_\text{nv}$）：每卡持有本节点 $n/g$ 一块的和。

    $$t_1 = \frac{g-1}{g}\cdot\frac{n}{B_\text{nv}}$$

  2. 节点间 all-reduce：各节点第 $i$ 号卡组成一个组，同时在各自的网卡上做大小为 $n/g$ 的 all-reduce。

    $$t_2 = 2\,\frac{m-1}{m}\cdot\frac{n/g}{B_\text{ib}}$$

  3. 节点内 all-gather，把完整结果发回本节点所有卡：

    $$t_3 = \frac{g-1}{g}\cdot\frac{n}{B_\text{nv}}$$

  4. 过网卡的字节数从 $\approx 2n$ 降到 $\approx 2n/g$，网络这一项被 $g$ 张网卡分摊。

NCCL 实际怎么做

NCCL 会建多个环（channel），不同的环走不同网卡，节点间流量同样被多张网卡分摊，所以真实的「平铺」all-reduce 接近层次化的数字；上图的单环只用来说明瓶颈在哪一跳。集群网络通常按「轨道」（rail）布线：各节点的第 $i$ 号网卡接到同一组交换机，层次化第 2 步里的第 $i$ 号卡之间只隔一跳。

这就是并行维度的摆放规则：通信最频繁、消息又在关键路径上的维度（张量并行，每层都要 all-reduce 激活）放在节点内；通信能和计算重叠的维度（数据并行、流水线并行的点对点）放到节点间。完整的排法见 多维组合。

NCCL 与 torch.distributed

NCCL（NVIDIA Collective Communications Library）把每个集合通信实现成 CUDA kernel，直接在 GPU 之间经 NVLink、PCIe 或网卡（GPUDirect RDMA）搬数据，不经过 CPU。PyTorch 的 torch.distributed 在 GPU 上默认用它做后端。

  • 算法：Ring、Tree；CollNet（借助 InfiniBand 交换机的 SHARP 在网络里做归约）；NVLS（NCCL 2.17 起，在 Hopper 一代的 NVSwitch 上做 NVLink SHARP，归约在交换机里完成）；PAT（2.23 起，all-gather / reduce-scatter）。
  • 协议：Simple、LL、LL128。LL 系列用标志位做细粒度同步，延迟低、有效带宽低一些；Simple 用内存栅栏，适合大消息。NCCL 按消息大小和拓扑自动选算法与协议，可用环境变量 NCCL_ALGO、NCCL_PROTO 强制指定，NCCL_DEBUG=INFO 打印它选了什么、建了哪些环。
  • channel：每个 channel 是一个 CTA（线程块），占一个 SM。通信 kernel 和计算 kernel 同时跑时会抢 SM 和显存带宽，所以「重叠」并不完全免费。
import os, torch, torch.distributed as dist
dist.init_process_group("nccl")              # torchrun 设好 RANK / WORLD_SIZE / MASTER_ADDR
torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))
p = dist.get_world_size()
x = torch.randn(1 << 20, device="cuda")

dist.all_reduce(x, op=dist.ReduceOp.SUM)                 # 原地求和
out = torch.empty(p * x.numel(), device="cuda")
dist.all_gather_into_tensor(out, x)                      # 拼接所有 rank 的 x
y = torch.empty(x.numel() // p, device="cuda")
dist.reduce_scatter_tensor(y, x)                         # 求和后每人留 1/p
z = torch.empty_like(x)
dist.all_to_all_single(z, x)                             # 第 j 块发给 rank j

work = dist.all_reduce(x, async_op=True)   # 立即返回，通信排在 NCCL 的流上
# ... 这里可以继续排不依赖 x 的计算 ...
work.wait()                                # 让当前 CUDA 流等通信完成（不阻塞 CPU）

子组用 dist.new_group(ranks) 建；多维并行用 init_device_mesh("cuda", (dp, tp), mesh_dim_names=("dp", "tp")) 一次建好每一维的组，见 多维组合。

易错：卡住不动

同一组里的所有 rank 必须以相同顺序调用相同的集合通信，张量大小也要一致。某个 rank 因为分支条件少调一次 all_reduce，其它 rank 不会报错，而是一直等，直到超时（init_process_group 的 timeout）后 watchdog 才把进程杀掉。常见诱因：只在 rank 0 上做的评测里调用了集合通信、各 rank 的 batch 数不同、MoE 里某些专家没收到 token 就跳过了通信。

自测

8 卡用 ring 对 1 GB 梯度做 all-reduce，每张卡发出多少字节？

$2\cdot\frac{7}{8}\cdot 1\text{ GB} = 1.75$ GB，收进也是 1.75 GB。卡数再多，这个数也不会超过 2 GB。

ring 的带宽项与卡数无关，为什么上千卡时还要换 tree？

ring 的延迟项是 $2(p-1)\alpha$，随卡数线性增长；消息不大时它占了大头。double binary tree 的延迟项是 $2\lceil\log_2 p\rceil\alpha$，带宽项仍约 $2n\beta$，所以在卡多、消息中小时更快。

nccl-tests 在 8 卡上测 all-reduce，algbw = 200 GB/s，busbw 是多少？该和什么比？

$200 \times \frac{2\cdot 7}{8} = 350$ GB/s。和单张卡单方向的链路带宽比，例如 H100 NVLink4 的 450 GB/s。

为什么说 all-reduce = reduce-scatter + all-gather 不只是一个实现技巧？

两半各需要每卡收发 $\frac{p-1}{p}n$，加起来正好是 all-reduce 的带宽下界 $2\frac{p-1}{p}n$。ZeRO / FSDP 把这两半拆开、中间插进优化器更新或前向计算，总通信量不变。

8 卡张量并行，如果 4 张在节点 A、4 张在节点 B，会怎样？

环里有两跳要走网卡，整个 all-reduce 降到网卡速度。H100 + NDR 下单方向 450 vs 50 GB/s，约慢 9 倍，而且张量并行的通信在每层的关键路径上，无法藏到计算后面。

all-to-all 和 all-gather 每卡收发量都是 $\frac{p-1}{p}n$，区别在哪？

all-gather 每人收到的是同一份数据，可以用树、交换机内复制（NVLS）等方式省带宽；all-to-all 每对 rank 之间是不同的数据，没有冗余可省。MoE 里每对之间的量还取决于路由结果，负载不均时最慢的那对决定时间。

训练卡住不动、没有报错，GPU 利用率 100%，最可能是什么？

某个 rank 少调或多调了一次集合通信，其它 rank 的 NCCL kernel 在 GPU 上自旋等待（所以利用率显示很高）。用 NCCL_DEBUG=INFO、PyTorch 的 flight recorder 或 py-spy 看各 rank 停在哪一次调用。
